# 向量数据库

> [!abstract] 一句话定义
> 专门存储和检索高维向量的数据库，核心能力是**近似最近邻搜索（ANN）**——在百万级向量里毫秒级找出最相似的 Top-K。

## 为什么重要

[[RAG]] 的检索底座。没有它，每次问答都要全量比对数百万条 [[Embedding]]，延迟无法接受。

## 核心原理

### ANN 索引

暴力检索是 O(n)，ANN 用少量精度损失换巨大速度提升：

| 算法 | 思路 | 特点 |
| --- | --- | --- |
| HNSW | 多层可导航小世界图 | 查询快、内存占用高，最常用 |
| IVF | 先聚类再只搜最近的桶 | 内存友好，需训练 |
| PQ / 量化 | 压缩向量 | 省内存，损失精度 |
| DiskANN | 磁盘上的图索引 | 超大规模、省内存 |

### 关键参数

- `M` / `efConstruction` / `efSearch`（HNSW）：召回率 vs 延迟的旋钮
- 距离度量：cosine / dot / L2 —— 必须和 [[Embedding]] 训练方式一致
- 过滤（filter）：先过滤再搜 vs 先搜再过滤，结果差别很大

### 选型维度

| 维度 | 说明 |
| --- | --- |
| 部署形态 | 嵌入式 / 单机 / 分布式 |
| 混合检索 | 是否原生支持 BM25 + 向量 |
| 元数据过滤 | RAG 里几乎必用（按文档、时间、权限筛） |
| 成本 | 内存是最贵的资源 |

### 常见选项

- 嵌入式（零运维）：FAISS、Chroma、LanceDB、SQLite-VSS
- 服务化：Milvus、Qdrant、Weaviate、pgvector（复用 Postgres）

> [!tip] 实用建议
> 数据量 < 10 万条时，先用 pgvector 或嵌入式方案。**不要为了向量专门引入一套分布式系统**，除非规模真的到了。
