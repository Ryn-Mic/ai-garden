# 上下文工程

> [!info] 阅读定位
> **进阶研究 · 技术研究**。上下文组织的工程视角；普通用户版见 [[concepts/AI能看到什么|AI能看到什么]]。

> [!abstract] 一句话定义
> 系统性地决定「这一次推理，窗口里到底该放什么」。可以理解为 [[concepts/提示工程|提示工程]] 的系统化升级版——从"写好一句话"变成"管理一整条上下文流水线"。

## 为什么重要

[[concepts/大语言模型|大语言模型]] 的上下文窗口再大也是有限且昂贵的资源。上下文里塞什么、按什么顺序放、什么时候压缩，直接决定 Agent 能不能跑完长任务。

## 核心原理

### 窗口里通常有四类东西

| 类别 | 内容 | 主要风险 |
| --- | --- | --- |
| 系统提示 | 角色、规则、工具说明 | 太长会稀释注意力 |
| 检索内容 | [[concepts/RAG|RAG]] 召回的片段 | 无关片段污染判断 |
| 对话历史 | 多轮交互 | 无限增长，必须压缩 |
| 工具结果 | 函数/API 返回 | 体积不可控，常需截断 |

### 关键手法

- **压缩**：滚动摘要旧对话、只保留结论
- **卸载**：把大块内容写进文件/数据库，窗口里只留引用路径（Agent 场景常用）
- **隔离**：子任务用独立上下文，只回传结论
- **排序**：重要信息放开头或结尾（"中间遗忘"现象）
- **预算**：给每类内容设 token 上限

> [!tip] 一句话判断
> 如果一个 Agent 在长任务中"越跑越傻"，八成是上下文管理问题，不是模型问题。
