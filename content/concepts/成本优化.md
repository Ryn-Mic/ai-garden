# 成本优化

> [!info] 阅读定位
> **进阶研究 · 开发者**。降低 AI 使用成本的技术策略；普通用户可先关注免费优化（Tool Search、输出截断）。

> [!abstract] 一句话定义
> 在不牺牲最终效果的前提下，通过技术手段降低 [[concepts/大语言模型|大语言模型]] 和 [[concepts/Agent|Agent]] 系统的使用成本。

## 为什么重要

AI Agent 的成本主要来自：
- **Token 消耗**：输入和输出都计费，长上下文成本呈指数增长
- **API 调用频率**：Agent 循环中的每次决策都是一次调用
- **模型选择**：能力强的模型价格可能贵 10-100 倍

一个未优化的 Agent 在复杂任务中可能消耗数百万 tokens，成本从几美元飙升到上百美元。合理优化可以在保持效果的同时降低 70-90% 的成本。

### 💰 成本计算基础

**什么是 Token？**
Token 是 AI 处理文本的基本单位。详见 [[concepts/Token|Token]]。

粗略估算：
- 英文：1 token ≈ 4 个字符 ≈ 0.75 个单词
- 中文：1 token ≈ 1.5-2 个汉字

**价格示例**（2026 年参考）：
| 模型 | 输入价格 | 输出价格 | 适用场景 |
| --- | --- | --- | --- |
| Claude Opus | $15/M tokens | $75/M tokens | 复杂推理、代码生成 |
| Claude Sonnet | $3/M tokens | $15/M tokens | 日常任务、简单代码 |
| GPT-4o-mini | $0.15/M tokens | $0.60/M tokens | 简单分类、格式化 |

**实际案例**：
```text
任务：分析 10 个代码文件（共 50K tokens）+ 生成报告（5K tokens）

未优化方案：
- 每次加载全部工具定义：50K tokens
- 每个文件单独分析：10 次调用
- 使用 Claude Opus
成本：(50K + 50K) × 10 × $15/M + 5K × 10 × $75/M = $18.75

优化后方案：
- Tool Search：省掉 50K × 10 = 500K tokens
- 批处理：10 个文件 1 次调用
- Prompt Caching：第 2-10 次请求 90% 缓存命中
- 弱模型执行，强模型审查
成本：≈ $2.50

节省：87%
```

## 优化策略分类

### 🔥 一级：上下文优化（热门、稳定、零影响）

#### 1. Tool Search / 延迟加载工具列表

**原理**：不在每次请求中加载所有工具定义，只按需加载。

**通俗理解**：就像菜单点餐，传统方式是把整本菜谱（200 道菜的详细做法）都告诉 AI，而 Tool Search 只先给菜名列表，AI 需要哪道菜的做法时再单独查询。

```text
❌ 传统方式：加载 200 个 MCP 工具 → 每次请求增加 ~50K tokens
✅ Tool Search：只加载 name 列表 → 按需查询 → 节省 95% 工具定义成本
```

**什么是工具（Tool）？**
工具是 AI Agent 可以调用的功能，比如"读取文件"、"搜索网页"、"查询数据库"等。每个工具都有名称和详细说明（schema），说明会占用大量 tokens。

**实现方式**：
- [[concepts/MCP|MCP]] 服务器只返回工具名称列表（如 `read_file`, `search_web`）
- Agent 需要使用某个工具时，通过 `ToolSearch` 动态获取该工具的详细说明
- Claude Code 默认采用此方式

**节省**：50K-200K tokens/请求（取决于工具数量）

#### 2. Bash 输出截断

**原理**：命令输出通常只有前几行或最后几行有用。

```text
❌ 返回完整日志：10000 行 → 300K tokens
✅ 智能截断：前 50 行 + 后 50 行 → 3K tokens
```

**实现**：
- 使用 `head -n 50` 和 `tail -n 50`
- 对 `ls`、`git log`、`npm install` 等命令自动截断
- 保留关键信息（错误、警告、摘要）

**节省**：平均每次命令 10K-500K tokens

#### 3. Prompt Caching（提示缓存）

**原理**：重复的上下文（系统提示、文件内容、工具定义）缓存 5 分钟，后续请求以 10% 价格读取。

**通俗理解**：就像餐厅把你的常点菜记下来。第一次点菜要完整说明，之后 5 分钟内只需说"还是老样子"，服务费便宜 90%。

```text
第一次请求：100K tokens × $15/M = $1.50
后续 5 分钟内：100K cached × $1.5/M + 10K new × $15/M = $0.30
节省：80%
```

**什么会被缓存？**
- **系统提示**（System Prompt）：告诉 AI 你的身份和规则的固定文本
- **工具定义**：AI 可用的功能列表
- **大文件内容**：你让 AI 分析的代码或文档

**触发条件**（Anthropic 为例）：
- 缓存块 ≥ 1024 tokens（约 700 个中文字）
- 5 分钟内的重复请求
- 缓存块在请求中的位置相同

**如何用好缓存？**
- 将固定内容（系统提示、工具定义、大文件）放在请求的**前面**
- 保持上下文结构稳定，不要频繁调整顺序
- 避免频繁修改 prompt 开头部分

**节省**：70-90% tokens 成本（高频场景）

#### 4. 选择性文件读取

**原理**：只读必要的文件部分，而不是全文。

```text
❌ Read 整个 10000 行文件 → 300K tokens
✅ Read file:1000-1100 → 3K tokens
✅ Grep 定位后 Read 相关部分 → 5K tokens
```

**实现**：
- 使用 `Read` 的 `offset` 和 `limit` 参数
- 先 `Grep` 定位，再精确读取
- 避免反复读取同一文件

**节省**：每次 50K-500K tokens（大文件场景）

### 🔵 二级：架构优化（稳定、可能影响交互）

#### 5. 分层模型策略（Router Pattern）

**原理**：用强模型规划，用弱模型执行。

**通俗理解**：就像建筑项目中，总工程师（强模型）负责设计方案和关键决策，普通工人（弱模型）负责具体施工。大脑决策用贵的，体力活用便宜的。

```text
强模型（Opus/GPT-4）：
  - 制定计划（"先做 A，再做 B，最后验证 C"）
  - 复杂决策（"这个 bug 可能是 X 或 Y 导致的"）
  - 代码审查
  成本：$15/M tokens

弱模型（Sonnet/GPT-4o-mini）：
  - 执行已定计划（按步骤 1-2-3 做）
  - 简单代码修改（改个变量名、加个注释）
  - 格式化、翻译
  成本：$3/M tokens
```

**什么是强模型和弱模型？**
- **强模型**：推理能力强，能处理复杂问题，但价格贵（如 Claude Opus、GPT-4）
- **弱模型**：适合简单任务，速度快价格低（如 Claude Sonnet、GPT-4o-mini）

**如何实现？**
- [[research/products/Claude-Code|Claude Code]] 的 `/plan` 命令：主 Agent 制定计划 → 子 Agent 执行
- LangChain 的 `RouterChain`：自动根据任务类型选择模型
- 自定义路由逻辑：写代码判断任务复杂度

**节省**：总成本降低 50-70%（长任务）

#### 6. 上下文压缩 / 摘要

**原理**：将历史对话压缩为摘要，而不是保留全文。

```text
原始历史（10 轮对话）：200K tokens
压缩后（摘要 + 最近 3 轮）：30K tokens
```

**实现**：
- 每 N 轮对话后，用模型生成摘要
- 只保留关键决策和状态
- 丢弃冗余的中间过程

**风险**：可能丢失细节，适合不需要回溯的任务

**节省**：60-80% 上下文成本（长会话）

#### 7. 流式输出 + 提前停止

**原理**：实时检测输出质量，必要时提前终止。

```text
模型开始输出无关内容 → 立即停止 → 重新提示
避免生成 5000 tokens 的无效输出
```

**实现**：
- 使用 `stream: true`
- 监控输出 token，检测重复、跑题
- 动态调整 `max_tokens`

**节省**：10-30% 输出成本

### 🟢 三级：工程优化（高效但需要权衡）

#### 8. 批处理（Batching）

**原理**：将多个独立任务合并为一次请求。

```text
❌ 单独处理 10 个文件 → 10 次 API 调用
✅ 一次请求处理所有文件 → 1 次调用
```

**限制**：
- 总 tokens 不能超过上下文窗口
- 任务必须独立（无依赖关系）

**节省**：减少固定开销（系统提示、工具定义重复）

#### 9. 本地模型混用

**原理**：简单任务用本地模型（Ollama、llama.cpp），复杂任务用云端 API。

```text
本地（Llama 3.2 3B）：
  - 代码格式化
  - 简单问答
  - 分类、提取
  成本：$0

云端（Claude Opus）：
  - 复杂推理
  - 代码生成
  成本：$15/M tokens
```

**权衡**：本地模型能力弱，需要准确判断任务复杂度

**节省**：20-50% 总成本（混合场景）

#### 10. RAG 优化

**原理**：只检索最相关的片段，而不是加载整个知识库。

**什么是 RAG？**
RAG（检索增强生成）是让 AI 从大量文档中找到相关信息再回答问题的技术。详见 [[concepts/RAG|RAG]]。

**通俗理解**：就像考试时翻书找答案。笨方法是把整本教科书都复印给 AI（贵），聪明做法是先用目录找到相关章节，只复印那 3 页（便宜）。

```text
❌ 加载 100 个文档 → 500K tokens
✅ Embedding 检索 Top 3 → 15K tokens
```

**如何优化？**
- 使用 [[concepts/向量数据库|向量数据库]] 精确检索（把文档变成数字，计算相似度）
- 调整检索数量（`top_k`）：不要一次取太多文档
- **Rerank 二次筛选**：第一轮粗选 20 个，第二轮精选 3 个

**具体流程**：
1. 用户问题 → 转为向量（Embedding）
2. 在向量数据库中搜索最相似的 Top 20 文档片段
3. 用 Rerank 模型重新排序，取 Top 3
4. 只把这 3 个片段发给 AI 回答

**节省**：80-95% 知识库成本

#### 11. 结果缓存（应用层）

**原理**：相同输入直接返回缓存结果，不调用模型。

```text
用户问："什么是 Transformer？"
第一次：调用模型 → 1K tokens
后续：返回缓存 → 0 tokens
```

**实现**：
- Redis/Memcached 缓存 (query → response)
- 设置合理过期时间
- 处理缓存失效逻辑

**节省**：重复查询场景可达 100% 节省

#### 12. Few-shot → Zero-shot 渐进

**原理**：先用 few-shot 验证效果，稳定后改为 zero-shot。

**什么是 Few-shot 和 Zero-shot？**
- **Few-shot**：给 AI 几个示例，教它怎么做
  ```
  示例1: 输入"天气不错" → 输出"正面"
  示例2: 输入"真糟糕" → 输出"负面"
  示例3: 输入"还行吧" → 输出"中性"
  现在分析: "今天真开心" → ?
  ```
- **Zero-shot**：直接下指令，不给示例
  ```
  请判断以下文本的情感（正面/负面/中性）: "今天真开心"
  ```

**通俗理解**：就像学开车，教练最初会示范几次（few-shot），熟练后只需说"去超市"就能自己开（zero-shot）。

```text
开发阶段：3 examples × 500 tokens = 1.5K tokens/请求
生产阶段：优化 prompt → 0 examples → 节省 1.5K tokens/请求
```

**什么时候可以去掉示例？**
- 模型足够强（如 Claude Opus、GPT-4）
- 任务足够简单（常见的分类、翻译）
- Prompt 描述足够清晰

**节省**：10-30% prompt 成本

### 🟡 四级：高级策略（需要深度定制）

#### 13. 蒸馏（Distillation）

**原理**：用强模型生成训练数据，训练小模型替代。

**什么是蒸馏？**
就像学徒跟着大师学手艺。让强模型（老师）做 10000 道题并给出答案，然后用这些答案训练小模型（学生），最终学生能以 1/20 的成本完成相同任务。

**通俗理解**：
- **传统方式**：每次都请顶级专家（$100/小时）
- **蒸馏方式**：请专家示范 100 次，培养实习生（$5/小时），以后用实习生

```text
强模型（Claude Opus）→ 生成 10K 训练样本
  问题: "天气不错" → 答案: "正面情感"
  问题: "真糟糕" → 答案: "负面情感"
  ... 10000 个示例

弱模型（Fine-tuned Llama 3.2）→ 学习这 10K 样本
部署后：成本降低 95%，延迟降低 10 倍
```

**适用场景**：
- 高频任务（每天调用上万次）
- 重复任务（客服分类、情感分析、格式化）
- 可定义任务（有明确的输入输出规则）

**不适用**：需要推理、创造性、处理未见过的问题

**节省**：90-95% 成本（但需要前期训练投入）

#### 14. Speculative Decoding（推测解码）

**原理**：用小模型快速生成草稿，大模型并行验证。

**什么是 Speculative Decoding？**
这是一种让 AI 生成更快的技术。小模型先快速"猜"10 个词，大模型同时验证这 10 个词对不对，错的重新生成。

**通俗理解**：就像学生先快速答题（小模型），老师批改时大部分都对（大模型验证），只需改少数错误。总时间接近学生答题速度，质量接近老师亲自答。

```text
小模型生成 10 tokens → 大模型验证 → 8 个正确 → 只付 2 个 token 的推理成本
总延迟接近小模型，质量接近大模型
```

**好处**：
- 速度快（接近小模型）
- 质量高（接近大模型）
- 成本低（只为错误的 tokens 付费）

**限制**：需要模型提供商支持这个功能（如 Anthropic Extended Thinking）

**节省**：20-40% 推理成本 + 大幅降低延迟

#### 15. 动态上下文窗口

**原理**：根据任务复杂度动态调整上下文大小。

```text
简单任务：8K 窗口 × $3/M = 低成本
复杂任务：200K 窗口 × $15/M = 高能力
```

**实现**：
- 任务分类器判断复杂度
- 自动选择合适的上下文配置

## 成本监控与度量

### 关键指标

| 指标 | 说明 | 目标 |
| --- | --- | --- |
| Cost per Task | 单任务成本 | < $0.10（简单任务） |
| Token Efficiency | 有效 tokens / 总 tokens | > 60% |
| Cache Hit Rate | 缓存命中率 | > 70% |
| Model Mix Ratio | 强模型 / 总调用 | < 30% |

### 工具

- **Anthropic Console**：Token 统计、Caching 命中率
- **LangSmith**：链路追踪、成本分析
- **Helicone**：跨厂商成本监控
- 自建：日志 + 数据库 + 仪表盘

## 最佳实践总结

### ✅ 优先级排序

1. **先做零成本优化**：Tool Search、输出截断、选择性读取
2. **再上 Caching**：70-90% 节省，但需要 prompt 工程
3. **考虑分层模型**：长任务或高频场景，ROI 最高
4. **最后定制方案**：蒸馏、本地模型（需要工程投入）

### ⚠️ 避坑指南

| 陷阱 | 后果 | 解决 |
| --- | --- | --- |
| 过度压缩上下文 | 模型失去关键信息，效果下降 | 保留最近 N 轮完整对话 |
| 盲目用弱模型 | 任务失败 → 重试 → 成本更高 | 建立任务复杂度评估 |
| 缓存键设计不当 | 返回错误结果 | 包含关键参数（用户ID、版本） |
| 没有监控 | 不知道钱花在哪 | 必须记录每次调用成本 |
