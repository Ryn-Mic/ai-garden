# Agent

> [!info] 阅读定位
> **进阶研究 · 技术研究**。原理与执行循环；普通用户先看 [[tutorials/basics/通用Agent的使用|通用Agent的使用]]。

> [!abstract] 一句话定义
> 让 [[concepts/大语言模型|大语言模型]] 从「回答问题」变成「完成任务」：给它目标、工具和循环，它自己决定下一步做什么。

## 为什么重要

基础模型通过输入信息生成输出，但不会凭自身获得当前日期、数据库访问或发邮件的权限。应用可以提供日期、图像、检索结果等上下文，并为它配置工具；所以“模型知道什么”和“应用能做什么”要分开讨论。

Agent 做的，是围绕目标、工具与反馈组织执行，给模型配上一双**手**：让它能搜索、读文件、调 API、跑代码、查数据库——把文字变成动作。而且每做完一个动作，它还会看一眼结果，再决定下一步，直到任务完成。

这是"聊天"和"干活"的分界线。

## 一个例子：Agent 是怎么干活的

假设你对一个 Agent 说："查一下深圳明天的天气，要下雨就提醒我带伞。"

背后发生的事，其实是这么一个循环：

1. **思考**：「我的知识停在训练截止那天，明天的天气必须现场查。」
2. **行动**：调用天气查询工具，参数是城市=深圳。
3. **观察**：工具返回——大雨，22 度。
4. **再思考**：「信息够了，不用查别的了。」
5. **回答**：「深圳明天有大雨，记得带伞。」

有一件事值得说破：**模型自己并没有上网**。它从头到尾只在做一件事——看着当前手里的全部信息，决定"下一步该用哪个工具、传什么参数"，或者"信息够了，可以收工了"。真正动手执行的是外围的宿主程序，执行完把结果塞回对话，模型再接着想。

> [!tip] 心智模型：一个极速但粗心的实习生
> 把 Agent 想成一个打字极快、知识面极广、但**完全没记性、也不会主动核实**的实习生：
> - 你不交代清楚目标，它就自由发挥（见 [[concepts/幻觉|幻觉]]）；
> - 你不给它工具，它就只能空谈；
> - 你不告诉它什么时候收工，它会一直干到把预算烧完。
>
>用好 Agent 的全部技巧，本质上就是**当好这个实习生的项目经理**。

## 核心原理

### 最小循环

```text
观察(Observation) → 思考(Thought) → 行动(Action) → 结果 → 再观察 ... → 直到完成
```

这就是 [[concepts/提示工程|提示工程]] 里常说的 **ReAct** 模式（Reason + Act，边想边做）。

一个 Agent 系统 = **模型 + 工具 + 循环 + 记忆 + 停止条件**。五个词缺一不可，少一个都会翻车，下面挨个拆开讲。

### 模型：决策大脑

Agent 的一切判断都由模型做出，所以模型能力直接决定上限。这里有个反直觉的事实：**平时聊天里表现"差不多"的模型，放进 Agent 里差距会被急剧放大**。

原因是 Agent 场景对模型的要求高得多——它要能：

- 严格按 [[concepts/Token|Token]] 结构拼出工具调用的 JSON，一个逗号都不能错；
- 看懂工具返回的报错信息，并据此改换策略，而不是傻乎乎原样重试；
- 在十几轮对话累积下来的一堆中间结果里，仍然记得最初的目标。

所以搭 Agent 时，别省模型钱：推理能力第一梯队的模型（Claude 3.5 Sonnet、GPT-4o、DeepSeek-V3 级别）和弱模型之间，是"能用"和"完全不可用"的差距。

### 工具：与外界交互的手脚

模型怎么知道有哪些工具、每个工具怎么用？靠**工具描述**——一段写在提示词里的说明书。

这就像抽屉上贴的标签：标签写得含糊，再聪明的人也会拿错抽屉。**工具调用出问题，八成不是模型笨，是描述写得差**。一条好描述要说清三件事：

1. 这个工具是干什么的；
2. 什么情况下**该**用它，什么情况下**不该**用；
3. 每个参数的格式和范围（比如"搜索关键词用空格分隔的名词，不要写长句"）。

把工具接口标准化、让所有 Agent 都能即插即用的协议，见 [[concepts/MCP|MCP]]。

### 记忆：跨步骤保持状态

模型的参数是冻结的，Agent 的"记性"完全靠工程手段搭出来，分两层：

- **短期记忆**：就是上下文窗口。本质是把整个任务的过程——你的指令、每一步的思考、每次工具的返回——**全部抄写在一张工作台上**。工作台就这么大（见 [[concepts/上下文工程|上下文工程]]），任务一长，中间结果会把台面堆满，模型开始"看不见"最早的目标。这是长任务越跑越傻的根源。
- **长期记忆**：靠 [[concepts/RAG|RAG]] 和 [[concepts/向量数据库|向量数据库]]。把资料存进"档案柜"，用到时按语义相似度取回，而不是全抄在工作台上。

### 控制流：循环、分支、停机

控制流是 Agent 的**护栏系统**，负责回答三个问题：

- 什么时候必须停下来？（最大轮数、预算上限、超时熔断）
- 什么动作不能自动执行？（发邮件、删文件、写数据库——必须先过人工审批）
- 任务跑到哪一步算完成？（显式的完成判定，而不是"模型自己觉得做完了"）

没有护栏的 Agent 就像没有刹车的车——平时看不出区别，出事就是大事。

## 扩展 Agent 的两条路：MCP 与 Skill

四件套装齐，Agent 只是「能跑」。要让它越用越强，有两条互补的扩展路线：

**接工具——[[concepts/MCP|MCP]]**。工具是 Agent 的手脚，但过去每接一个工具都要写一套私有适配：3 个应用 × 10 个工具 = 30 套胶水代码。MCP 把接口标准化成「AI 应用的 USB-C」：工具方写一次 Server，所有支持协议的 Agent 都能即插即用。

**教方法——[[concepts/Skill|Skill]]**。光有手脚还不够，会做事靠的是章法。Skill 把「某类任务怎么干好」（流程、经验、好例子坏例子）写成一份手册，Agent 遇到这类活才翻开——平时不占上下文，用时按需加载。

再加上喂事实的 [[concepts/RAG|RAG]]，三条路线各管一段：

| | 给 Agent 的是什么 | 类比 |
| --- | --- | --- |
| [[concepts/MCP|MCP]] | 能力（工具、数据源） | 接一双手 |
| [[concepts/Skill|Skill]] | 章法（流程、经验） | 发一本 SOP 手册 |
| [[concepts/RAG|RAG]] | 事实（资料、知识） | 往档案柜存文件 |

**MCP 管「能干什么」，Skill 管「怎么干好」，RAG 管「依据是什么」。**

## 常见架构

四种经典套路，按复杂度从低到高：

- **ReAct**：边想边做，每步看结果再决定下一步。最通用，适合"不知道要查几轮"的探索型任务。
- **Plan-and-Execute**：先让模型列一份完整计划，再逐项执行。适合路径清晰的长任务；缺点是计划赶不上变化，中途出错要重新规划。
- **Reflection（反思）**：干砸了不硬着头皮重试，而是先复盘"我为什么失败"，把教训写进上下文再试一次。对工具报错特别有效。
- **Multi-Agent（多智能体）**：把任务拆给多个角色协作（规划者/执行者/审查者）。听起来美好，实际成本高、调试极难——**只在任务确实能拆分、且分工明确时才用**。

### Workflow vs Agent

用厨房打个比方：

- **Workflow（工作流）**是一份写死的菜谱：第几步放盐、火候多大，全部事先定好，模型只负责每一步里面的具体活（比如"把这段话总结一下"）。稳定、便宜、可预测。
- **Agent** 是请了位主厨：你只说"做一桌好菜"，步骤他临场自己定。灵活，但可能翻车，也更贵。

> [!tip] 选型原则
> 路径能提前写死，就用工作流；只有"下一步做什么"必须看情况临场判断时，才上 Agent。
> 实践中最常见也最稳的形态是：**工作流做骨架，其中某几个节点里放一个小 Agent**。

## 两种 Agent：通用与专用

按干活的领域，Agent 分两大门类，用法和工具链完全不同：

| | **通用 Agent** | **专用 Agent** |
| --- | --- | --- |
| **干什么** | 查资料、读网页、整理文档、串自动化流程 | 深耕一个垂直领域，如写代码、管数据库 |
| **靠什么工具** | 搜索、网页抓取、表格、邮件、知识库 | 代码仓库索引、语法树分析、终端执行 |
| **代表** | [[research/products/Dify|Dify]]、扣子（Coze）上的各类助理 | [[research/products/Claude-Code|Claude Code]]、[[research/products/Cursor|Cursor]] |
| **上手教程** | [[tutorials/basics/通用Agent的使用|通用Agent的使用]] | （待补） |

## 最常见的失败模式

> [!warning] 避坑清单
> - **工具描述含糊** → 模型调错工具或乱传参数。这比模型能力不足常见得多：先改描述，再怪模型。
> - **没有停机条件** → 模型钻进死循环，一轮轮烧 Token，直到你手动掐断。
> - **上下文爆炸** → 中间结果（尤其整页网页原文）把工作台堆满，模型后半程开始失忆和胡言乱语。
> - **过早多 Agent** → 复杂度翻倍，收益接近零。单 Agent + 工作流能解决 90% 的问题。
