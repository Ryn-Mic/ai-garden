# Skill

> [!info] 阅读定位
> **工具箱 · 入门**。不要求编程。本文帮你判断 Skill 有没有用；具体加载步骤见 [[tutorials/skills/Skill从加载到验证|Skill从加载到验证]]，技术机制另见 [[research/analysis/Skill的加载机制与遵循边界|Skill的加载机制与遵循边界]]。

## 先看一个你可能遇到的问题

你每周让 AI 整理周报，每次都要重复交代：

> 按「完成事项、待办、风险」分类。负责人和日期必须来自原文；没有写就标为待确认。不要把建议写成已经完成的工作。

这段要求就是可以沉淀成 Skill 的经验。以后做同类任务时，让应用找到并加载它，可以减少重复交代和格式漂移。

**Skill 像一份可复用的工作说明书，不是换了一个更聪明的模型。**

## 用生活化的场景理解

想象你在咖啡店点单，有两种方式：

### 方式 A：每次都从头说

```
“我要一杯咖啡”
店员：”什么咖啡？”
“美式”
店员：”大中小？”
“中杯”
店员：”热的还是冰的？”
“冰的”
店员：”糖和奶要吗？”
“不要糖，加燕麦奶”
```

### 方式 B：用暗号

```
“还是老样子”
店员：”好的，中杯冰美式，燕麦奶，不加糖”
```

**Skill 就是那个”老样子”** —— 把你重复说的要求，打包成一个可复用的配方。

但注意两个关键点：
1. **要先建立这个”配方”**：第一次还是要说清楚全部细节
2. **店员要认识这个暗号**：应用要支持 Skill 机制，并且能找到你定义的那份

## 它里面有什么

采用 Agent Skills 格式的 Skill 通常是一个文件夹：

```text
weekly-summary/
├── SKILL.md       ← 名称、适用场景和工作步骤
├── references/    ← 可选：参考说明、术语表、示例
├── assets/        ← 可选：模板文件、格式样例
└── scripts/       ← 可选：要执行的程序（有安全风险）
```

### 核心文件：SKILL.md

这是唯一必需的文件，通常包含：

```markdown
# Weekly Summary Skill

## 触发场景
当用户要求整理周报、周总结、weekly summary 时使用本技能。

## 工作流程
1. 识别输入：会议记录、聊天记录、工作日志
2. 按以下结构分类：
   - **已完成**：本周交付的工作，必须有完成证据
   - **进行中**：正在做但未完成的，标注进度百分比
   - **待办**：下周计划，标注负责人和截止日期
   - **风险与阻塞**：影响进度的问题，标注严重程度
3. 验收标准：
   - 每项必须注明原文依据
   - 没有日期/负责人的标记为”待确认”
   - 不能把讨论中的想法写成已决定的事项
```

**两个关键部分：**

1. **简介（触发场景）**：告诉应用或 [[concepts/Agent|Agent]]「什么时候考虑用它」
2. **正文（工作流程）**：告诉 Agent「这类任务怎样完成、怎样验收」

### 可选的扩展资料

| 文件/目录 | 作用 | 例子 |
| --- | --- | --- |
| `references/` | 详细说明、术语表、边界案例 | 什么算”已完成”，什么算”进行中” |
| `assets/` | 模板文件、格式示例 | 周报的 Markdown 模板 |
| `scripts/` | 自动化脚本 | 从 Git 提交记录生成周报初稿 |

> [!warning] 安全提示
> 带 `scripts/` 的 Skill 会执行代码，不能因为它叫”说明书”就忽略风险。
> 
> **来源不明的 Skill 不要直接运行**，尤其是那些要求：
> - 访问你的文件系统
> - 连接网络
> - 执行 shell 命令
> - 读取环境变量或密钥

## 真实场景：什么时候值得用 Skill

### ✅ 值得用的场景

#### 1. 固定格式的重复任务

**痛点**：每次都要纠正同样的格式错误

```
你第 1 次让 AI 整理客户反馈：
“按产品、问题、影响分类”

AI 输出：混在一起，没分清楚

你第 2 次：
“按产品、问题、影响分类。每条必须包含客户名称和日期。”

AI 输出：分类对了，但把猜测的影响写成了事实

你第 3 次：
“按产品、问题、影响分类。每条必须包含客户名称和日期。
影响要区分'客户明确说的'和'我们推测的'。”

AI 输出：终于对了
```

**如果你每周都要做一次客户反馈整理，这就是做成 Skill 的时机。**

把这三轮纠正的经验写进 `customer-feedback-skill/SKILL.md`：

```markdown
## 分类规则
- 产品：客户使用的产品/功能模块
- 问题：客户描述的具体问题（原话引用）
- 影响：
  - 【客户明确】：客户直接说的影响（如”导致订单丢失”）
  - 【推测】：从描述推断的影响

## 必需字段
- 客户名称（来自原文）
- 反馈日期（来自原文，找不到标记”日期待确认”）
- 原文依据（哪一段话）

## 禁止事项
- 不要编造客户没说的影响
- 不要把”我们打算做”写成”已经做了”
```

以后每次整理，只要说”用 customer-feedback 技能整理这份反馈”，就能复用这套经验。

#### 2. 需要多步验证的专业流程

**场景**：技术文档审查

```markdown
# Tech Doc Review Skill

## 检查清单
1. **代码示例**：
   - 是否可以直接运行
   - 依赖是否声明
   - 版本号是否最新
   
2. **API 文档**：
   - 参数类型是否标注
   - 必需/可选是否说明
   - 错误码是否完整

3. **安全检查**：
   - 是否包含硬编码的密钥/token
   - 敏感信息是否脱敏
   
4. 输出格式：
   问题列表 + 严重程度（高/中/低）+ 建议修改
```

这类 Skill 的价值在于**把隐性的专业经验显性化**，让 AI 按专家的检查清单工作。

#### 3. 跨团队协作的标准化输出

**场景**：产品需求文档（PRD）模板

不同人写的 PRD 格式千差万别，用 Skill 统一：

```markdown
# PRD Writing Skill

## 必需章节
1. 需求背景（用户痛点 + 数据支撑）
2. 目标用户（画像 + 使用场景）
3. 功能描述（核心流程 + 边界情况）
4. 验收标准（可量化的指标）
5. 技术约束（性能/兼容性/安全）

## 每个功能点必须回答
- 为什么要做（价值）
- 谁来用（用户）
- 怎么用（流程）
- 怎么算完成（验收）

## 输出格式
Markdown + Mermaid 流程图
```

团队约定”用 PRD 技能写需求”，新人也能输出符合规范的文档。

### ❌ 不适合用 Skill 的场景

| 情况 | 为什么不用 | 应该怎么做 |
| --- | --- | --- |
| 只问一次的问题 | 写 Skill 的时间比直接说还长 | 直接在聊天里说清楚要求 |
| AI 无法访问数据源 | Skill 本身不提供数据访问能力 | 先解决数据接入（[[concepts/MCP\|MCP]]） |
| AI 经常编造信息 | Skill 不能强制消除[[concepts/幻觉\|幻觉]] | 提供证据 + 人工核对 |
| 需要调用外部 API | Skill 是流程说明，不是工具 | 用 [[concepts/MCP\|MCP]] 或应用自带集成 |

**核心判断标准**：如果这个任务你**会重复做 3 次以上**，并且**每次的要求是稳定的**，就值得做成 Skill。

支持 Agent Skills 机制的应用，工作流程通常是：

```
1. 扫描阶段（应用启动时）
   └─ 读取所有 Skill 的名称、描述、触发关键词
   
2. 匹配阶段（你发起任务时）
   └─ 应用根据你的要求，判断哪些 Skill 可能相关
   
3. 加载阶段（决定使用某个 Skill）
   └─ 把 SKILL.md 的内容读入[[concepts/上下文|上下文]]
   └─ 可选：加载 references/ 和 assets/
   
4. 执行阶段
   └─ AI 按 Skill 里的流程工作
   └─ 如果有 scripts/，可能会执行代码
```

**三个关键认知：**

1. **安装成功 ≠ 本轮已加载**
   - Skill 可能被扫描到了，但这次任务没触发
   - 查看应用的 Skill 调用日志（如果有）来确认

2. **已加载 ≠ 一定遵循**
   - Skill 是加到[[concepts/上下文|上下文]]里的”说明书”，不是强制执行的程序
   - AI 仍可能因为理解偏差、[[concepts/上下文|上下文]]过长等原因偏离
   - 验收靠的是**检查输出**，不是信任加载记录

3. **不同产品的行为差异很大**
   - 扫描范围：有的只扫描特定目录，有的扫全局
   - 触发方式：有的自动匹配，有的需要你明确指定
   - 权限策略：有的会弹权限确认，有的直接执行

如果应用不支持 Agent Skills，把 SKILL.md 的内容复制粘贴到聊天里**仍然有用**，但这是”提供[[concepts/提示工程|提示词]]模板”，不等于完成了原生 Skill 安装。

## 从哪里找现成的 Skill

### 官方来源

1. **[Anthropic 官方 Skills 仓库](https://github.com/anthropics/skills)**
   - 文档处理、代码审查、写作辅助等
   - 详见 [[toolbox/skills/文档处理Skills|文档处理Skills]]
   - 质量有保障，但数量有限

2. **应用内置市场**
   - Claude Code、WorkBuddy、Qoder 等都有技能市场
   - 操作见 [[tutorials/skills/Skill从加载到验证|Skill从加载到验证]]
   - 通常经过基本审核

### 社区来源

3. **[skills.sh](https://skills.sh)**
   - 社区发现入口，收录第三方 Skill
   - ⚠️ 收录不等于官方审核，使用前需要自己评估

4. **GitHub 搜索**
   - 搜索关键词：`agent-skills` `SKILL.md`
   - 查看 Star、最近更新、作者背景

### 挑选 Skill 的安全检查清单

在安装任何 Skill 之前，检查这些：

| 检查项 | 为什么重要 | 怎么检查 |
| --- | --- | --- |
| **作者身份** | 来路不明的可能有恶意代码 | 官方账号 > 知名开发者 > 匿名 |
| **实际步骤** | 确认流程符合你的需求 | 读完整个 SKILL.md |
| **附带程序** | scripts/ 里的代码可能访问文件/网络 | 有 scripts/ 就要审查代码 |
| **权限需求** | 读写文件、网络访问、环境变量 | 看说明文档和代码 |
| **维护记录** | 长期无更新可能有兼容性问题 | 最近更新时间、Issue 回复 |
| **用户反馈** | 实际使用效果 | Star 数、Issue 区、评论 |

> [!danger] 红线警告
> **永远不要**直接运行：
> - 要求 sudo 权限的
> - 代码混淆的（比如 base64 编码的 shell 命令）
> - 访问 ~/.ssh、~/.aws 等敏感目录的
> - 联网发送数据却不说明发往哪里的

**Star 数和下载量只能帮助发现，不能代替安全审查和自己的试用。**

## 自己写一个能解决什么

最适合写的是**你已经重复确认过的工作规则**，而不是一句「你是 XX 专家」。

### 有效的 Skill

```markdown
# Customer Feedback Analysis

## 输入识别
包含以下任一关键词即视为客户反馈：
- 客户反馈、用户反馈、bug 报告
- 客服记录、工单内容

## 分类规则
1. 产品模块：根据功能路径或客户描述匹配
2. 问题类型：
   - 功能缺失：”希望有 XX 功能”
   - 功能异常：”XX 点了没反应”
   - 体验问题：”找不到 XX 在哪”
3. 严重程度：
   - P0：影响核心流程，有客户明确表示影响业务
   - P1：影响使用体验，有明确抱怨
   - P2：优化建议

## 输出格式
| 模块 | 问题 | 严重程度 | 客户 | 日期 | 原文依据 |

## 验收标准
- 严重程度必须有原文支撑，不能靠猜
- 客户名称和日期来自原文，找不到标记”待确认”
```

### 无效的 Skill

```markdown
# Customer Feedback Analysis

你是一位资深的客户成功专家，请用专业的视角分析客户反馈。
```

**区别在哪？**

- ❌ 第二个只是角色扮演，没有给出**可执行的规则**和**可验证的标准**
- ✅ 第一个给出了清晰的分类逻辑、判断依据、输出格式

### 从零开始写一个纯文字 Skill

完整练习见 [[tutorials/skills/Skill从加载到验证#自己做一个纯文字 Skill|创建纯文字 Skill 的练习]]。

基本步骤：

1. **收集三次真实任务**
   - 做同一类任务三次
   - 记录每次你纠正了什么
   
2. **提炼出稳定规则**
   - 哪些要求是每次都要说的
   - 哪些错误是每次都会犯的
   
3. **写成结构化说明**
   ```markdown
   ## 任务识别
   关键词、触发场景
   
   ## 工作流程
   1. 第一步做什么
   2. 第二步做什么
   
   ## 验收标准
   - 必须包含 XX
   - 不能出现 XX
   
   ## 常见错误
   - 错误 A：正确做法是 XX
   - 错误 B：正确做法是 XX
   ```

4. **用测试材料验证三次**
   - 准备 3 份测试数据
   - 每次让 AI 按 Skill 执行
   - 记录哪里还不够清楚，补充规则

5. **逐步增加要求**
   - 不要一开始就写得很复杂
   - 每次加一条规则，验证一次
   - 最终形成稳定版本

## 边界：它不是强制执行器

写「必须」可以表达要求，却**不能保证模型绝不违反**。

### Skill 能做什么

- ✅ 提供清晰的流程和标准，减少格式漂移
- ✅ 把隐性经验显性化，让输出更一致
- ✅ 节省重复交代的时间

### Skill 不能做什么

- ❌ **强制执行**：模型仍可能因为理解偏差、上下文过长而偏离
- ❌ **消除幻觉**：Skill 不能阻止模型[[concepts/幻觉|编造信息]]
- ❌ **提供数据**：Skill 是流程说明，不能让 AI 访问它本来访问不了的数据
- ❌ **替代权限控制**：涉及删除、外发、支付的操作，必须靠应用权限，不能只靠 Skill 里的”禁止”

**安全原则**：

涉及这些操作时，必须依靠**应用权限、审批和人工验收**，不能只靠 Skill 中的禁止语句：

- 删除文件或数据
- 发送邮件或消息
- 调用付费 API
- 修改生产环境
- 访问敏感信息

## 三种扩展能力的区别

选择能力扩展时记住：

| 扩展方式 | 给 AI 提供的是 | 类比 | 适用场景 |
| --- | --- | --- | --- |
| **[[concepts/MCP\|MCP]]** | 外部工具（读网页、查数据库、调 API） | 给实习生接一双手 | 需要访问外部数据源 |
| **[[concepts/Skill\|Skill]]** | 工作流程（怎么做、怎么验收） | 给实习生发一本 SOP 手册 | 有重复的标准化任务 |
| **[[concepts/RAG\|RAG]]** | 检索到的资料（知识库、文档） | 给实习生准备一个档案柜 | 需要基于大量文档回答 |

**它们可以协作，不互相替代：**

```
场景：自动生成周报

1. MCP 工具：从 Git/Jira 读取本周的提交和工单
   └─ 解决”数据从哪来”
   
2. Skill 说明：周报的格式、分类规则、验收标准
   └─ 解决”怎么整理”
   
3. RAG 检索：查找相关的项目背景、术语表
   └─ 解决”补充上下文”
```

**MCP 管「能干什么」，Skill 管「怎么干好」，RAG 管「依据是什么」。**
