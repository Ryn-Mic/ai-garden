# MCP

> [!info] 阅读定位
> **工具箱 · 入门**。不要求编程。先判断你是否需要接入工具；协议、服务端代码放在 [[research/analysis/MCP的接入与调用机制|MCP的接入与调用机制]]。

## 从一个日常问题开始

你让 AI 总结某个网页。它能写摘要，却可能没有打开网页的能力，只能根据链接或标题猜内容。

一种解决办法是让你正在用的 AI 应用接入一个网页读取工具。**MCP（模型上下文协议）就是应用与这类外部工具通信的一种标准方式**。

它像统一插口，但不是某一个插件，也不是”装上以后就什么都能做”。

## 用生活化的场景理解

### 类比：厨房的标准插座

想象你有一个厨房（AI 应用），想用各种电器（外部工具）：

**没有标准插口的时代：**

```
买了意大利咖啡机 → 要专门找意大利电工改电路
买了日本电饭煲 → 又要请日本电工重新布线
买了德国烤箱 → 再请德国电工...
```

3 个电器 = 3 套不同的接线方式 = 3 个电工

**有了标准插座（MCP）之后：**

```
所有电器都用统一的插头
只要插上插座就能用
换电器不用重新布线
```

**MCP 就是 AI 应用的”标准插座”：**

- **之前**：每个 AI 应用接入一个外部工具，都要写一套专门的适配代码
- **现在**：工具只要支持 MCP 协议，任何支持 MCP 的应用都能即插即用

### 现实例子

**场景 1：读取网页内容**

- **传统方式**：
  - Claude Code 要写一套网页读取适配
  - Cursor 要写另一套
  - ChatGPT 要写第三套
  - 同一个功能，写 3 遍代码

- **MCP 方式**：
  - 开发者写一个 MCP Server（提供网页读取功能）
  - Claude Code、Cursor、ChatGPT 都支持 MCP
  - 配置一次，三个应用都能用

**场景 2：查询公司数据库**

- **传统方式**：每个 AI 应用都要单独对接你的数据库，写认证、查询逻辑
- **MCP 方式**：写一个 MCP Server 封装数据库访问，配好权限，所有支持 MCP 的应用都能查

## 你实际接入的是什么

MCP 不是一个具体的工具，而是一套**通信协议**。要理解几个关键概念：

| 名称 | 用普通话理解 | 例子 |
| --- | --- | --- |
| **AI 应用（Client）** | 你正在操作的软件 | Claude Code、Cursor、WorkBuddy |
| **MCP Server（服务端）** | 提供外部能力的程序 | 网页读取服务、数据库查询服务 |
| **工具（Tool）** | 服务端开放的具体动作 | 读取 URL、搜索文件、执行 SQL |
| **资源（Resource）** | 服务端提供的数据源 | 特定文件、数据库表、API 端点 |
| **授权（Permission）** | 允许访问的范围 | 只读某文件夹、不允许删除 |

### 完整的调用链路

<iframe src=”/assets/mcp-call-sequence.html” width=”100%” height=”600” frameborder=”0”></iframe>

```
你：”总结这个网页的内容”
   ↓
AI 应用分析：需要读取网页内容
   ↓
AI 决策：调用网页读取工具
   ↓
MCP Client（应用内置）→ 通过 MCP 协议 → MCP Server（网页读取服务）
   ↓
MCP Server 实际执行：打开 URL，抓取内容
   ↓
返回网页文本 → AI 应用 → 放入[[concepts/上下文|上下文]]
   ↓
AI 基于实际内容生成总结
```

**关键认知：**

- **模型不直接上网**：它只是”提出要用哪个工具”
- **应用负责执行**：真正打开网页、读文件的是应用和 MCP Server
- **模型只看结果**：它拿到的是”工具返回的内容”，然后继续推理

这就是 [[concepts/Agent|Agent]] 工作的核心循环。

## 什么时候需要它

**核心判断原则：先用自带的，不够用再接 MCP。**

很多 AI 应用已经内置了常用功能，不需要额外接 MCP：

| 需求 | 先尝试 | 什么时候再考虑 MCP |
| --- | --- | --- |
| **总结一份文件** | 直接上传文件 | 需要在固定目录持续查询多个文件 |
| **查询公开信息** | 应用内置搜索（如 Claude 的联网） | 需要访问特定数据源或内网资料 |
| **读一条网页** | 应用自带网页读取 | 原有工具不支持，或需要特殊认证 |
| **连接业务系统** | 官方集成（如 Slack、Notion） | 需要定制接口或特殊权限控制 |

### ✅ 适合用 MCP 的场景

#### 1. 持续访问本地文件系统

**场景**：你有一个项目目录，AI 需要频繁读取、搜索其中的文件

- **不用 MCP**：每次手动上传文件 → 麻烦，且 AI 看不到文件结构
- **用 MCP**：接入文件系统 MCP Server → AI 能列出目录、搜索文件、读取内容

**工具记录**：[[toolbox/mcp/文件系统MCP|文件系统MCP]]

#### 2. 访问需要认证的数据源

**场景**：查询公司内网的数据库、API、文档系统

- **不用 MCP**：手动导出数据粘贴给 AI → 繁琐，且数据可能过期
- **用 MCP**：写一个 MCP Server 封装认证和查询逻辑 → AI 能直接查询最新数据

**注意权限**：MCP Server 需要配置好访问控制，不能让 AI 随意读写生产数据。

#### 3. 调用特定的 API 或服务

**场景**：AI 需要调用天气 API、翻译服务、内部工具

- **不用 MCP**：你手动调 API 再粘贴结果 → AI 无法自主决策何时查询
- **用 MCP**：把 API 封装成 MCP Server → AI 能在需要时自动调用

#### 4. 多个应用共享同一数据源

**场景**：Claude Code 和 Cursor 都要访问同一个知识库

- **传统方式**：分别为两个应用写适配 → 重复劳动
- **MCP 方式**：写一个 MCP Server，两个应用都配置它 → 维护一处，到处可用

### ❌ 不适合用 MCP 的场景

| 情况 | 为什么不用 | 应该怎么做 |
| --- | --- | --- |
| 只查一次的临时需求 | 配置 MCP 的时间比手动操作还长 | 直接粘贴或上传 |
| 应用已有内置功能 | 重复建设，且内置的通常更稳定 | 先用内置功能 |
| 你不熟悉命令行/编程 | 部署 MCP Server 需要技术背景 | 找技术同事协助或先学习基础 |
| 敏感数据且无权限控制 | 风险高 | 先设计好权限方案再接入 |

用途记录：[[toolbox/mcp/网页读取MCP|网页读取MCP]]、[[toolbox/mcp/文件系统MCP|文件系统MCP]]。

需要接入时，再看 [[tutorials/mcp/MCP从接入到验收|MCP从接入到验收]]（进阶使用，需要运行环境）。

**重要区分**：网页读取、搜索、浏览器操作是**三种不同能力**，不能把名字相近的服务当作等价替代。

## 接入之前准备什么

如果确定需要接 MCP，按这个清单准备：

### 1. 确定应用支持

不是所有 AI 应用都支持 MCP，查官方文档确认：

- **支持 MCP 的应用（部分）**：
  - Claude Desktop（官方客户端）
  - Claude Code
  - Cursor（部分功能）
  - Cline（VS Code 插件）

- **查看方法**：
  - 搜索应用文档里的”MCP”关键词
  - 查看设置里是否有 MCP 配置入口
  - 看应用版本要求（有些功能只在新版本）

**没有 MCP 入口不要盲目套用别的软件配置** —— 不同应用的配置文件位置、格式、启动方式都可能不同。

### 2. 确认服务来源

MCP Server 可以是：

| 类型 | 特点 | 来源 | 风险等级 |
| --- | --- | --- | --- |
| **官方 Server** | Anthropic 或应用开发商提供 | GitHub 官方仓库 | ✅ 低 |
| **知名第三方** | 开源社区维护，Star 多 | GitHub、npm | ⚠️ 中（需审查） |
| **公司内部** | 技术团队自己开发 | 内网 GitLab | ⚠️ 中（看开发规范） |
| **来历不明** | 匿名、无文档、闭源 | 不明链接、私人分享 | ❌ 高（不建议用） |

**获取方式：**

- [Anthropic MCP Servers](https://github.com/modelcontextprotocol/servers) - 官方示例
- [MCP 服务目录](https://github.com/punkpeye/awesome-mcp-servers) - 社区整理
- 应用文档推荐的服务

**安全检查：**

```bash
# 拿到 Server 后，先看这几点：
1. README 是否说明功能和权限
2. 代码是否开源（能审查）
3. 最近更新时间（长期无维护要警惕）
4. Issue 区是否有安全问题报告
5. 是否要求过高权限（如 sudo、读敏感目录）
```

### 3. 确认依赖与费用

不同类型的 MCP Server 要求不同：

| Server 类型 | 依赖 | 费用 | 例子 |
| --- | --- | --- | --- |
| **本地程序** | Node.js / Python 运行环境 | 免费 | 文件系统 MCP |
| **远程服务** | 网络连接 + API Key | 可能按调用计费 | 天气 API MCP |
| **自托管** | 服务器 + 数据库 | 服务器成本 | 内网知识库 MCP |

**检查依赖：**

```bash
# 本地 MCP Server 通常要求
node --version  # 需要 Node.js（看 README 要求的版本）
python --version  # 或 Python
```

**费用透明：**

- 本地 Server（读文件、执行命令）：通常免费
- 调用外部 API 的 Server：可能有 API 费用，查看对应服务的定价
- 把内容送到远程的 Server：确认数据去向和隐私政策

### 4. 划定权限

在配置 MCP Server 之前，想清楚：

**数据访问边界：**

- ✅ 可以读哪些目录/数据库/API
- ❌ 禁止访问什么（敏感文件、生产数据库）
- ⚠️ 是否会把数据发到远程（搜索、翻译类 Server）

**操作权限：**

- 只读 vs 可写
- 能不能删除文件
- 能不能执行命令

**最小权限原则：**

```
❌ 错误：给 AI 访问整个用户目录 (~/)
✅ 正确：只给访问项目目录 (~/projects/my-app)

❌ 错误：数据库 Server 有删除表权限
✅ 正确：只给 SELECT 查询权限
```

## 怎么接入

**这是具体应用的差异，不存在一份适用于所有 Agent 的安装路径。**

### 图形化配置（简单）

有些应用提供图形界面：

```
1. 打开应用设置
2. 找到”MCP 服务”或”工具”选项
3. 点击”添加服务”
4. 填写：
   - 服务名称（自己起个好记的）
   - 服务类型（本地程序 / 远程 API）
   - 启动命令或 URL
5. 保存并测试连接
```

### 配置文件（常见）

大多数应用需要编辑配置文件（通常是 JSON）：

**例子：Claude Desktop 的配置**

文件位置：`~/Library/Application Support/Claude/claude_desktop_config.json`（macOS）

```json
{
  “mcpServers”: {
    “filesystem”: {
      “command”: “npx”,
      “args”: [
        “-y”,
        “@modelcontextprotocol/server-filesystem”,
        “/Users/yourname/projects”
      ]
    },
    “web-reader”: {
      “command”: “node”,
      “args”: [
        “/path/to/web-reader-server/index.js”
      ],
      “env”: {
        “API_KEY”: “your-api-key-here”
      }
    }
  }
}
```

**配置说明：**

- `filesystem`、`web-reader`：服务名称（你自己定义）
- `command`：启动 Server 的命令
- `args`：命令参数（如 Server 脚本路径、配置参数）
- `env`：环境变量（如 API Key，**不要提交到 Git！**）

### 权限确认

配置好后，应用通常会：

1. **首次连接时弹窗**：询问是否允许该 Server 访问
2. **显示 Server 提供的工具列表**：让你确认哪些功能会暴露给 AI
3. **运行状态指示**：显示哪些 Server 已连接、哪些失败

**如果配置后看不到这些，说明配置可能有问题：**

- 检查配置文件语法（JSON 格式是否正确）
- 查看应用日志（通常在”开发者工具”或日志文件）
- 确认 Server 启动命令能在终端单独运行

## 连上了怎样判断成功

**「连接正常」≠「本次任务调用了它」**

### 验证层次

#### 第 1 层：服务连接成功

应用显示 MCP Server 状态为”已连接”或”运行中”。

**这只证明**：应用能启动 Server 并通信  
**不能证明**：AI 实际用了它

#### 第 2 层：工具调用记录

AI 在工作时显示了工具调用步骤，例如：

```
1. 思考：需要读取项目的 README 文件
2. 调用工具：filesystem.readFile(“/path/to/README.md”)
3. 返回：（文件内容）
4. 基于文件内容生成回答
```

**这证明**：AI 确实调用了 MCP 工具  
**不能证明**：返回内容是正确的

#### 第 3 层：结果验证

拿公开测试资料验证，检查：

| 验证项 | 怎么检查 | 通过标准 |
| --- | --- | --- |
| **工具被调用** | 查看应用的工具调用日志 | 有明确的调用记录 |
| **返回了内容** | 查看工具返回结果 | 不是错误，不是空 |
| **内容正确** | 对照原文 | AI 引用的事实能在返回内容中找到 |
| **AI 理解了内容** | 问具体细节 | 能准确回答返回内容里的具体信息 |

### 实战测试

**准备一个测试场景：**

```
场景：测试文件系统 MCP

1. 创建测试文件
   echo “项目名称：AI Garden” > ~/projects/test.txt
   
2. 让 AI 读取
   “读取 ~/projects/test.txt 的内容”
   
3. 验证点：
   ✓ 应用显示调用了 filesystem.readFile
   ✓ 返回内容包含”项目名称：AI Garden”
   ✓ AI 能准确回答”项目名称是什么”
   
4. 负向测试（重要！）
   “读取 ~/projects/nonexist.txt”
   ✓ AI 应该诚实说”文件不存在”
   ✗ 如果 AI 编造了内容，说明工具调用失败但它没意识到
```

**AI 自称「已经连接」「已经查询」不是独立证据。** 找不到调用记录时，应把结论标为未确认。

## 常见问题排查

### 问题 1：配置了但 AI 不用

**可能原因：**

- AI 判断不需要用工具（你的要求可以直接回答）
- 工具描述不清晰，AI 不知道何时该用
- 应用的触发策略问题

**排查方法：**

```
试试明确要求：
❌ “这个项目有哪些文件”（AI 可能猜测）
✅ “用文件系统工具列出 ~/projects/my-app 目录”（明确要求）
```

### 问题 2：显示调用了但返回错误

**可能原因：**

- 路径不对（权限配置的路径 vs 实际要读的路径）
- 权限不足（文件系统权限、API 认证失败）
- Server 进程崩溃了

**排查方法：**

1. 查看工具返回的错误信息（应用日志）
2. 手动执行同样的操作（如 `cat ~/projects/test.txt`）
3. 检查 Server 进程是否还在运行

### 问题 3：返回内容但 AI 理解错了

**这不是 MCP 的问题，而是 [[concepts/上下文|上下文]]处理问题：**

- 返回内容太长，超出上下文窗口
- 返回内容格式复杂（如大型 JSON），AI 解析错误
- 多个工具调用返回混在一起，AI 搞混了

**解决方法：**

- 让 Server 返回简化的结果
- 分步骤调用工具，而不是一次问太多
- 用 [[concepts/Skill|Skill]] 规定怎么处理工具返回

## 安全边界

**MCP 工具有实际权限，不是沙盒演示。**

### 只读也有风险

| 风险类型 | 具体场景 | 防护措施 |
| --- | --- | --- |
| **数据泄露** | 读取公司文件，内容送到 AI 提供方 | 只读非敏感文件，或用本地模型 |
| **提示词注入** | 网页中的恶意文字诱导 AI 改变任务 | 检查工具返回，设置输出过滤 |
| **隐私追踪** | 远程 Server 记录你的查询内容 | 审查 Server 代码，用开源方案 |

### 写操作必须有防护

涉及这些操作时，必须有**应用层权限控制**或**人工审批**：

- 删除文件或数据
- 修改数据库
- 发送邮件/消息
- 调用付费 API
- 执行 shell 命令

**不要指望 AI”很聪明不会误删”** —— [[concepts/幻觉|幻觉]]、理解偏差、上下文污染都可能导致误操作。

### 密钥管理

**永远不要：**

- ❌ 把 API Key 写在配置文件里并提交 Git
- ❌ 把密钥粘贴在聊天窗口
- ❌ 截图时包含密钥
- ❌ 用同一个密钥做所有事（无法区分哪个服务泄露）

**正确做法：**

- ✅ 用环境变量存密钥
- ✅ 每个服务用独立的受限 API Key
- ✅ 定期轮换密钥
- ✅ 配置文件用 `.gitignore` 排除

## Skill 与 MCP 怎么配合

两者解决不同问题，通常需要配合使用：

| | [[concepts/Skill\|Skill]] | MCP |
| --- | --- | --- |
| **解决什么** | 怎么做（流程、验收标准） | 能做什么（数据、工具） |
| **类比** | 操作手册 | 一双手 |
| **例子** | “整理周报要按这个格式” | “能读取 Git 提交记录” |

### 配合示例：自动周报

```
场景：每周五自动生成周报

MCP 工具：
- filesystem：读取项目文件
- git：查询本周提交记录
- jira：查询完成的工单

Skill 规定：
1. 从 Git 和 Jira 获取数据
2. 按「已完成、进行中、待办、风险」分类
3. 每项注明原始来源（commit hash、工单号）
4. 没有负责人的标记”待确认”
5. 输出 Markdown 格式
```

**有工具但没有验收，仍可能做错；有流程但没有工具，读不到数据。**

### 何时先装 MCP，何时先写 Skill

```
先确定任务类型：

纯文字任务（改写、总结、分类）
  ↓
  先写 Skill（如果是重复任务）
  不需要 MCP
  
需要外部数据（读文件、查数据库、调 API）
  ↓
  先接 MCP 工具（获取数据能力）
  ↓
  再写 Skill（规定怎么处理数据）
```

## 自己开发 MCP Server

如果现有的 MCP Server 都不满足需求，可以自己开发。

**前置要求：**

- 熟悉 Node.js 或 Python
- 理解 JSON-RPC 协议（MCP 基于此）
- 有权限访问要封装的数据源

**开发流程：**

1. **选择 SDK**：
   - [@modelcontextprotocol/sdk](https://github.com/modelcontextprotocol/typescript-sdk) (TypeScript)
   - [mcp-python-sdk](https://github.com/modelcontextprotocol/python-sdk) (Python)

2. **定义工具**：
   ```typescript
   server.tool({
     name: “readFile”,
     description: “读取指定路径的文件内容”,
     parameters: {
       path: { type: “string”, description: “文件绝对路径” }
     },
     handler: async ({ path }) => {
       // 实际读取文件的逻辑
       return { content: fileContent }
     }
   })
   ```

3. **权限控制**：
   - 参数验证（路径是否在允许范围）
   - 错误处理（文件不存在、权限不足）
   - 日志记录（谁访问了什么）

4. **本地测试**：
   ```bash
   # 启动 Server
   node your-server.js
   
   # 用 MCP Inspector 测试
   npx @modelcontextprotocol/inspector
   ```

5. **配置到应用**：
   按前面的配置方法接入
