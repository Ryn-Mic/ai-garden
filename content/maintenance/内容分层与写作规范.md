# 内容分层与写作规范

> [!info] 阅读定位
> **写作维护 · 进阶使用**。面向作者。正文按类型保存，学习顺序单独维护；难度、成熟度和实测状态分别标注。

## 1. 正文目录与系列分开

| 目录 | 放什么 | 不负责什么 |
| --- | --- | --- |
| `tutorials/` | 基础、软件、Skill、MCP 与开发操作教程 | 不把目录列表当作学习顺序 |
| `toolbox/` | Skill / MCP 推荐与自建用途记录 | 不把所有工具变成必装清单 |
| `concepts/` | 解释一个问题的独立知识点 | 不要求入门读者先读完整部词典 |
| `research/` | 机制剖析、产品与框架、选型、论文 | 不混成普通用户入门前置 |
| `series/` | 按目标排好的 `1 → 2 → 3` 引用路线 | 不复制文章正文，不为系列编号重命名原文 |

`maintenance/` 收纳 Obsidian、同步、部署与写作；`templates/`、`assets/` 是辅助目录，不作为额外学习主线。

```text
content/
├── index.md                  # 首页：先系列 01，再按需求扩展
├── series/                   # 01～05 有序路线
├── tutorials/                # basics / software / skills / mcp / development
├── toolbox/                  # skills / mcp
├── concepts/                 # 独立知识点，入门与技术内容分别标级
├── research/                 # analysis / products / comparisons / papers
├── maintenance/              # 作者维护入口
├── templates/                # 不发布
└── assets/                   # 图片与虚构练习包
```

**分类看主要用途，不看篇幅**：解释“上下文是什么”是知识点；说明“在哪里操作”是教程；记录“为什么用这个工具”是工具记录；研究“怎样实现、证据是什么”是深入研究。

`type` 表达文章形式，`track` 表达主要阅读任务，`difficulty` 表达门槛；不要求这三个字段和目录名完全相同。例如知识点可以服务使用教程，也可以服务技术研究。`track: guides` 是历史字段值，不是另一份教程目录。

## 2. 系列必须给出清楚的下一站

使用 `templates/系列.md`。每条路线至少写明：

1. **读者、目标与准备**：能完成什么，哪些前提确实必需。
2. **主线顺序**：连续的 `1 → 2 → 3`，引用已有正文或其中的章节。
3. **中途补课**：只链接当前阶段需要的独立知识点，说明在这一站之前还是之后读。
4. **完成标准**：读完不等于学会，写清可核对的产物或解释能力。
5. **退出与延伸**：选读、选做、新增门槛分开；允许完成当前目标后停止。

`sequence` 保存主线的完整路径，允许带章节；`knowledge_points` 保存被引用的独立知识点。它们与正文保持一致，方便检查断链和顺序遗漏。

同一正文可以被多条系列引用。正文末尾的「系列导航」按各系列分别列位置与下一站，不给多条路线强行指定一个全局前后顺序。

首页只保留从简单到深入的入口；详细课程放在系列页，分类列表放在各类型的 `index.md`，不要维护三份相同阅读路线。

## 3. 难度是另一条轴

| `difficulty` | 页面名称 | 判定标准 |
| --- | --- | --- |
| `beginner` | 入门 | 不要求编程，解释术语，操作不默认终端、依赖安装或公式 |
| `intermediate` | 进阶使用 | 已完成基本任务，开始配置、排查或设计流程；写明新增前提 |
| `advanced` | 技术研究 | 涉及实现、代码、协议、公式、论文或实验设计；明确前置知识 |

Skill 用途可以是入门知识点，加载机制可以是技术研究；MCP 的解释入门，不代表接入与开发也没有门槛。Dify 的低代码形式仍有模型、数据与权限前提。

## 4. 元数据、正文与链接都要一致

```yaml
type: tutorial
track: guides
# toolbox / guides / research / meta
audience: non-programmer
# non-programmer / practitioner / developer / maintainer
difficulty: beginner
# beginner / intermediate / advanced
status: growing
# 成熟度，不是难度或实测凭证
tags: [tutorial, track/guides, level/beginner]
verification: docs-only
```

普通文章和系列标题之后增加可见「阅读定位」；目录索引可以省略普通文章格式，但要说明读者和用途。元数据、标签、正文门槛一致。

**站内引用使用从 Vault 根开始的完整双链路径，不加开头的 `/`，带上简短显示名。** 例如：

```markdown
[[concepts/Skill|Skill]]
[[tutorials/skills/Skill从加载到验证|加载与验收]]
[[series/02-把工作流程变成Skill|系列 02]]
```

Obsidian 与 Quartz 统一使用 `absolute` / 完整 Vault 路径。旧页面地址放入 `aliases` 供跳转兼容；新正文引用当前路径。旧路径别名会与新路径拥有同名尾段，因此不再依赖 `shortest` 猜目标。

迁移时保留原始备份，更新正文引用与配置；检查别名没有覆盖现存页面、相互冲突或形成循环。`aliases` 不是第二份正文，也不应显示为另一个学习目录。

## 5. 工具记录与教程各自必须回答什么

### 工具记录

使用 `templates/Skill-MCP记录.md`，写清作用与收益、来源与适用环境、成本与权限、最小试用与验收、证据范围。自建工具还要解释现成方式为什么不够、维护成本是什么。

普通用户能阅读自建用途，不代表需要亲自开发工具或维护服务器。

### 入门教程

使用 `templates/教程.md`，至少提供：

1. 一个具体任务目标。
2. 软件形态、功能与必要准备。
3. 能复制或下载的完整材料。
4. 一次一个有限动作，写明预期结果。
5. 依据原文或实际产物的验收与失败处理。

术语在需要时解释；不必要的 API、JSON、CLI、源码移到知识点、技术选读或开发实践。更详细是补操作和证据，不是堆术语。

## 6. 同一问题的入门与研究解释分开

| 问题 | 入门知识或教程 | 技术解释 |
| --- | --- | --- |
| 本轮有哪些资料 | [[concepts/上下文|上下文]]、[[concepts/AI能看到什么|AI 能看到什么]] | [[concepts/上下文工程|上下文工程]] |
| Skill 为什么没效果 | [[tutorials/skills/Skill从加载到验证|加载与验收]] | [[research/analysis/Skill的加载机制与遵循边界|加载机制与遵循边界]] |
| MCP 有什么用 | [[concepts/MCP|MCP]]、[[toolbox/mcp/网页读取MCP|网页读取记录]] | [[research/analysis/MCP的接入与调用机制|接入与调用机制]] |

两种解释互链，但不要求普通用户先读技术版。知识点可以有小练习，其主要用途仍是解释问题。

## 7. 技术研究与证据等级

研究文章使用 `templates/研究.md`，区分研究问题与条件、机制与原始来源、实验与观察、限制与反例。没有执行的实验写成方案；旧代码示例或选型表不能当作通用结论。

| `verification` | 含义 | 必须说明 |
| --- | --- | --- |
| `unverified` | 线索或待核查记录 | 未确认部分，不作操作保证 |
| `docs-only` | 官方文档或原始资料整理 | 来源、日期、未实测范围 |
| `tested` | 指定环境的实际操作验证 | 版本、输入、实际结果、失败与局限 |
| `not-applicable` | 导航或写作说明，无操作与实验结论 | 不用此字段暗示实测 |

官网、Star、格式检查、站点构建都不等于客户端效果实测。截图去掉账号、令牌、个人路径与业务数据，并标明产品形态和观察范围。

当前：WorkBuddy 5.6.2 只观察了主菜单；Qoder 的入口与 MCP 配置来自官方文档；练习包格式和内容已检查。它们均不能据此升级为已完成产品实测。旧技术文章也尚未全面核验。

## 发布前检查

```bash
npm run build
node scripts/check-content.mjs
```

- [ ] 正文放在正确类型目录；系列只引用，没有复制正文。
- [ ] 系列顺序、补课点和每站验收完整；首页从最容易的任务开始。
- [ ] 完整路径双链、章节、系列导航和旧路径跳转有效。
- [ ] 安装、加载、执行与结果分别说明；证据与权限边界清楚。
- [ ] 按 [[maintenance/多端同步与发布流程|同步与发布流程]] 将目录、别名和内容同步回 Gitee 写作源。

`check-content` 检查结构与生成页面，不代替软件实测或研究事实核验。
