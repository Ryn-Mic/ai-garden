# Agent 失败时怎么排查：先找证据，不先换模型

> [!info] 阅读定位
> **上手指南 · 入门**。面向遇到答错、漏资料、Skill 没效果或工具没用上的普通用户。一次只检查一个阶段，不要求会编程。

## 先做一个缩小问题的动作

**保留失败的输入和输出，在新任务里用短材料复现。** 先不要删除原始结果，也不要一次换模型、换软件、装插件、改规则。

可以用 [[tutorials/basics/练习材料与验收|虚构练习包]]，避免排查过程反复上传敏感文件。本文是排查框架，不是已经证明适用于所有产品的故障定位算法。

## 按“任务 → 材料 → 能力 → 规则 → 结果”检查

| 阶段 | 你要确认什么 | 能看的证据 |
| --- | --- | --- |
| 任务 | 要做什么、怎样交付是否明确 | 本次要求、标准表头或样例 |
| 材料 | 正文是否真的提供或读取 | 附件、引用、读取记录、原文依据 |
| 能力 | 当前模式、工具与权限能否完成 | 功能状态、工具列表、审批或错误信息 |
| 规则 | 需要的说明或 Skill 是否进入本轮 | 已安装列表、加载提示或诊断记录 |
| 结果 | 实际交付是否符合原文和目标 | 打开文件、检查表格、核对实际动作 |

不要把所有问题都归为“模型不聪明”。同样也不要预设肯定是某一个阶段；证据不足就保持未确认。

## 情况 A：它像没读过资料，却回答得很完整

### 1. 确认材料真的在本次输入中

写了文件名、给了文件夹权限，或上传了附件，不等于模型已收到全部正文。见 [[concepts/AI能看到什么|AI能看到什么]]。

### 2. 要求返回一个可核对的原文片段

```text
请列出你依据的这份用户材料的文件名，并引用与该结论直接相关的原文。
如果没有读取或无法提取，直接说明，不根据文件名或常识补写。
```

引用和自述是辅助信息，优先结合应用的读取记录核对。

### 3. 用短文字区分读取问题与处理问题

把出错的三五行原文直接粘贴，再让它做同一件事。

短材料能做、附件不能做，优先排查上传、提取或上下文组织；两者都做错，再检查任务要求与事实处理。一次测试不足以锁定唯一原因。

## 情况 B：Skill 装了，仍不按规则输出

1. 在已安装列表核对真实名称、设备和启用状态。
2. 用产品支持的显式选择方式启动匹配任务。
3. 查看是否有正文加载证据，再对照输出验收。

具体步骤见 [[tutorials/skills/Skill从加载到验证|Skill从加载到验证]]。**未发现、未加载、已加载但没遵循是不同问题**，不是都靠重复写“必须”解决。

若看不到加载记录，可以说“输出不符合要求，加载状态未知”，不要先断言模型无视了已经加载的 Skill。

## 情况 C：MCP 连接正常，却没有查到资料

先找来自目标服务的工具列表和实际调用记录。如果它调用的是软件自带搜索，不能算刚接入的 MCP 生效。

```text
本次请只使用指定的网页读取工具获取这条公开测试链接。
请说明调用是否成功；失败时保留错误，不使用其他来源代替。
```

先用公开资料。启动错误、工具未暴露、没选择调用、网站拒绝访问分别处理，见 [[tutorials/mcp/MCP从接入到验收|MCP从接入到验收]]。

## 情况 D：读到了资料，仍编造日期或负责人

不要只说“认真一点”。指出一个具体字段，并给出原文：

```text
原文写的是“小陈整理客户常见问题，本次没有约定截止日期”。
你把日期写成了 6 月 12 日，这个日期没有依据。
请只修正这一字段为“待确认”，保持其他已核实信息不变。
```

如果反复出现，缩短输入，给出一个完整样例，再换一份含缺失信息的材料测试。只测试信息齐全的样例，发现不了这类问题。

## 情况 E：聊久了忘记格式，或前后要求打架

新开任务，重新提供**当前目标、最终规则、必要材料和输出样例**。不要把很长的旧聊天整体复制进去。

区分两种现象：

- **规则遗漏**：本来要求保留依据，后来输出没这个字段。
- **要求冲突**：同时要求“不得猜日期”和“所有日期必须填满”。

先消除冲突，再测试。Skill 不会仅因为名字或“必须”二字就自动拥有最高优先级；不同应用组装规则的方式不同。

## “遵循强度”怎样用普通话理解

| 你做的事 | 它主要帮助什么 | 不能把它当成什么 |
| --- | --- | --- |
| 强调要求、给样例、保存 Skill | 提醒 AI 怎样完成任务 | 永不违反的保证 |
| 固定表头、验收清单、结果检查 | 更容易发现遗漏和错误 | 事实自动正确的证明 |
| 限制文件范围、关闭写权限、要求审批 | 限制应用实际能执行的动作 | 只写在聊天里就生效的权限锁 |

不要给所有模型套一个“遵循率 90%”之类的固定数字。你能做的是在自己的任务和版本中重复测试，并保留失败记录。技术解释见 [[research/analysis/Skill的加载机制与遵循边界|Skill的加载机制与遵循边界]]。

## 如果涉及发送、删除或覆盖

先停止继续操作，再查看邮件、文件或业务系统的**当前真实状态**。取消任务不会自动撤销已完成的动作；不要未经检查就重试，以免重复发送或覆盖。

把错误修复与原任务分开，优先保护数据。权限和操作无法确认时，不继续扩大范围。

## 记录一个可复查的问题

```text
软件形态、版本和当前模式：
任务与输入材料：
预期结果：
实际失败字段或动作：
已确认的读取、加载、调用证据：
尚不能确认的阶段：
只改变了哪一个条件再次测试：
```

保留脱敏记录比只写“这个模型不好用”更有价值。
