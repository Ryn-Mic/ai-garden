# RAG 与微调

## 结论先行

> [!success] 选型建议
> **先 RAG。** 只有当问题的本质是"模型的**行为习惯**不对"而不是"模型**不知道**"时，才上微调。两者可以叠加，不冲突。

一句话判据：

```text
知识缺失 / 需要引用 / 更新频繁  →  RAG
格式不稳 / 语气不对 / 提示太长  →  微调
```

## 对比维度

| 维度 | [[RAG]] | [[微调]] |
| --- | --- | --- |
| 解决的问题 | 模型不知道 | 模型做得不好 / 不稳定 |
| 知识更新 | 改数据，**分钟级** | 重训，天级 |
| 可引用来源 | ✅ 天然可以 | ❌ 说不出来 |
| 幻觉 | 降低（有据可依） | 基本不改善 |
| 成本 | 检索+存储，低 | 数据标注 + 算力，中高 |
| 数据需求 | 原始文档即可 | 需要**标注好**的样本 |
| 延迟 | +检索耗时 | 无额外 |
| 上下文占用 | 吃掉窗口 | 不占 |
| 可解释性 | 高（能给出处） | 低（黑盒） |
| 上线速度 | 小时级 | 天到周 |
| 主要风险 | 检索质量不稳 | 灾难性遗忘、过拟合 |

## 分场景推荐

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 企业文档问答 | RAG | 知识频繁变，且必须给引用 |
| 客服话术统一 | 微调 | 是风格与格式问题 |
| 最新资讯问答 | RAG | 训练数据必然滞后 |
| 领域术语理解（法律/医疗） | 继续预训练 + RAG | 语言本身不同，再挂检索 |
| 超长系统提示（几千 token 的规则） | 微调 | 把规则压进权重，省窗口 |
| 结构化抽取、固定 JSON 输出 | 微调 或 强约束提示 | 先试提示 + 校验 |
| 需要"我不知道"的诚实回答 | RAG | 有检索边界可依据 |

## 组合拳

最实用的形态是两者叠加：

```text
微调：教会模型你的输出格式、术语习惯、思考方式
RAG ：提供每一次回答需要的事实依据
```

## 决策流程

```text
1. 先改提示 → 有效？ 收工（[[提示工程]]）
2. 问题是"缺知识"还是"缺引用"？ → RAG
3. 问题是"格式/风格/稳定性"？ → 微调
4. 两者都有？ → RAG 打底，微调调性
```
