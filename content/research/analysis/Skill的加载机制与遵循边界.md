# Skill 的加载机制与遵循边界

> [!info] 阅读定位
> **进阶研究 · 技术研究**。面向需要理解宿主实现或设计评测的读者。普通用户操作版见 [[tutorials/skills/Skill从加载到验证|Skill从加载到验证]]。

## 研究问题与结论范围

为什么同一份 Skill 安装后，有时有效、有时没被使用？“必须遵循”究竟能控制什么？

本文根据 Agent Skills 规范与应用文档整理一套分析框架。**未在所有产品中追踪完整输入，也没有执行下述对照实验**，不报告虚构的遵循率。

核心区分：**可发现、已加载、已遵循、产生正确交付物，是不同层次的状态。**

## 标准规定格式，宿主决定接入

Agent Skills 是开放格式：目录中的 `SKILL.md` 包含名称、描述和指令，可附带程序与资源。

格式相同不意味着运行行为相同。宿主仍要决定：

- 从哪里扫描、安装范围如何划分，以及是否启用。
- 元数据如何提供给模型或选择器，怎样触发。
- 正文和引用如何读取、截断、保留或卸载。
- 脚本怎样运行，以及工具与文件权限怎样控制。

因此，比较客户端必须先记录产品形态与版本，不能只用“都支持 SKILL.md”推出完全兼容。

## 渐进式加载：元数据、正文、附带资源

规范描述的渐进式披露可以理解为三个层次：

| 层次 | 常见内容 | 应观察的证据 |
| --- | --- | --- |
| 发现信息 | 名称、适用描述 | 当前范围的技能列表，提供给选择器的元数据 |
| 选中后的指令 | `SKILL.md` 正文 | 加载提示、读取记录或可检查的上下文组装日志 |
| 执行时所需材料 | references、assets、scripts | 实际读取与执行记录，不只看文件存在 |

“平时只提供名称和简介”不是“模型完全不知道 Skill 存在”，也不是“零上下文成本”。元数据本身仍可能影响选择并占用输入空间；某些宿主还可能采用搜索、过滤或显式选择。

资源路径存在，不代表正文、脚本源码和全部引用都进入同一次模型调用。脚本可以由宿主执行，模型只接收结果。

## 四类失败不要混成“提示词不够强”

| 失败点 | 例子 | 优先排查 |
| --- | --- | --- |
| 未发现 | 只把文件放进未被扫描的目录 | 安装范围、扫描方式、设备与启用状态 |
| 未加载 | description 不匹配，或者被相似 Skill 干扰 | 描述、选择日志、显式选择能力 |
| 已加载但未按要求执行 | 长任务中遗漏来源字段 | 冲突要求、上下文组织、样例与输出校验 |
| 按流程走但交付仍错 | 调用了文档工具，表格数据却有误 | 输入质量、工具返回、计算与独立验收 |

前两类属于发现与路由问题，后两类属于任务执行和质量问题。单纯增加“必须”“绝对”无法同时解决它们。

## “遵循强度”不是一条通用百分比

下面是**控制机制的区别**，不是对所有模型都成立的优先级排名：

| 机制 | 能控制什么 | 不能保证什么 |
| --- | --- | --- |
| Skill 中的自然语言规则 | 引导流程、给出示例和验收项 | 每次输出都满足规则 |
| 宿主组装的规则与角色 | 提供更明确的任务边界 | 所有冲突场景都不会误解 |
| 结构化输出与结果校验 | 检查字段、类型和部分格式 | 内容一定真实、意图一定正确 |
| 应用权限、工具审批、后端授权 | 阻止未被允许的动作，限制执行范围 | 已允许动作一定符合业务要求 |

Skill 被读入普通消息，不会仅因文件名变成最高权限指令。用户要求与 Skill 冲突时怎样处理，要看宿主如何组装输入和模型的指令规则；不能给出适用于所有产品的固定排序。

安全要求应尽量做成**执行侧的硬约束**。例如限制输出目录、拒绝未经审批的外发、使用只读账号，而不是把“不得泄露数据”写进 Skill 后就取消权限管理。

## 一个可复现但尚未执行的对照实验

### 1. 固定实验条件

记录产品形态、版本、模型标识、安装范围、可用工具、测试材料和 Skill 文件版本。关闭与本任务无关的技能与外部写权限。

### 2. 建立三组条件

- A：不加载 Skill，使用同一份基础任务与材料。
- B：允许应用自动选择目标 Skill。
- C：使用产品支持的方式显式选择目标 Skill。

“没有加载”需要用日志确认；若 A 组实际自动加载了，不能当作有效基线。若产品没有对应控制能力，记录实验限制，不伪造隔离条件。

### 3. 为每组准备相同样例

至少包含：信息齐全、缺失日期、讨论事项未决定、材料中含有试图改变任务的文字。把最后一种视作不可信资料，不赋予工具权限。

每组先重复 5 次，保留输入、实际加载证据、输出与失败样本。这只是试验起点，不足以证明普遍可靠。

### 4. 分别计量路由与交付

- **加载率**：观察到目标正文加载的运行数 / 可检查的运行数。
- **交付通过率**：通过原文与格式验收的运行数 / 总运行数。
- **加载后通过率**：已确认加载且通过验收的运行数 / 已确认加载的运行数。

不可观察的加载状态记为 unknown，不按成功处理。内容验收优先用确定性字段比较和人工原文核对，不以模型自评替代。

### 5. 控制结论范围

如果 C 优于 B，可能是选择路由问题；如果二者都经确认加载但仍失败，再研究指令冲突、材料质量和上下文保留。

仅凭这组实验不能把差异归因到某个单一机制，也不能推广到其他模型、任务或版本。改变一个变量再复测。

## 当前仍需要进一步研究的内容

- 长任务和上下文压缩后，规则与关键证据如何保留。
- 多 Skill 冲突、工具依赖缺失与描述匹配的影响。
- 宿主可观察性不足时，如何诚实标注证据和实验限制。
